# v1 — Income forecast + Cashflow ledger + Rules engine + Safe-to-Spend

> Implementation plan. **✅ EXECUTED (June 2026).** All three layers shipped: income
> recurrence → `project_cashflows` → forecast; `safe_to_spend()` + the sectioned gear;
> the rules engine (notify/allocate/roundup + the v2 `categorize` action) hooked into
> `TransactionService.create`. The v4 enablers are in place: generic rule target
> (`target_kind`/`target_id`), `birth_year`, and `RuleExecution` storing
> `amount_cents` + `action_type` + `fired_at`. Deferred items live in [v2.md](./v2.md).
> Note: the live DB in this tree is `finance_tracker.db` (not `budget_ai.db`); a
> pre-migration backup sits at `finance_tracker.db.pre-v1.bak`.

## Context

The cashflow forecast projects **recurring expenses only** — a **schema gap**, not a logic
bug: `Expense` has a `recurrence` column (`server/src/db/models.py:107`) and `Income` does
not. So the forecast walks bills *down* from the current balance and never adds the paycheck
back, making `will_go_negative` falsely pessimistic.

This plan closes that gap and builds the two layers it unlocks, **integrating them into
surfaces that already exist** rather than adding tabs / cards / pages. Hard constraint: no
clutter, concise, don't overwhelm the user — *evolve existing components, use compound
components.*

The work decomposes into four layers, of which we build A (ledger) and B (rules):

| Layer | What it is | Features it powers |
| --- | --- | --- |
| **A — Scheduled cashflow ledger** | recurring income + expenses projected on read | Forecast, Safe-to-Spend |
| **B — Event-driven rules engine** | "on transaction X, do Y" | Qapital automations, round-ups |
| C — Query/analytics (deferred) | slice spending like a database | Lunch Money query tool → v2 |
| D — Gamification (declined) | reward/presentation | → v2 |

## Holistic UI principle (read first)

The app already has the right surfaces; we make them smarter, we do **not** add siblings:

| New capability | Lives in (existing surface) | NOT a new… |
| --- | --- | --- |
| Safe-to-Spend (real, dynamic) | **`SpendCard`** (already titled "Safe-to-Spend") | card |
| The rules behind that number | **`SpendSettingsDialog`** gear (already there) | settings page |
| Forecast (income + expense) | **`TimelineCard`** (already a spend timeline) | chart / page |
| Recurring income input | the existing income entry form | form |
| Auto-fund rules (round-up / allocate) | **Goal edit dialog** on the Goals page | "Automations" tab |
| Alert rules (notify) | **Budget** category (already emits overrun alerts) | tab |

**Compound components** carry the new complexity without visual clutter:

- `SafeToSpend` compound — `SpendCard` becomes the namespace; `SafeToSpend.Settings` (the
  gear dialog) and `SafeToSpend.Plan` (a "$X/day for N days" line) are subcomponents.
- `SpendSettingsDialog` becomes **sectioned** (compound) — *Horizon / What counts /
  Savings* — instead of a flat two-input form.
- One reusable `RuleEditor` (condition + action + target) is embedded in the Goal dialog now
  and reused for budget alerts; never its own page.

## Decisions (locked)

- **Rules v1 actions (all virtual):** Notify, Allocate-to-goal, Round-up-to-goal.
  (Auto-categorize already exists in `categorization_service.py`; not rebuilt.)
- **Why virtual, not real transfers:**
  - Real *external* transfers = regulated money transmission (Plaid Transfer / Dwolla /
    Stripe + KYC + ACH/NACHA + settlement + reversals). Today's Plaid usage is read-only.
  - Even *intra-app* balance writes desync from Plaid-synced balances (next sync overwrites).
  - `Goal.progress` is a virtual earmark bucket — safe to write, survives re-syncs.
- **Earmarks reduce Safe-to-Spend:** current `Goal.progress` is subtracted from the
  Safe-to-Spend number (YNAB / envelope effect — "the money's gone" without moving it), so a
  round-up that adds $5 to a goal immediately drops the spendable number by $5. This keeps
  virtual savings from being a toothless counter.
- **Safe-to-Spend = dynamic AND anchored:** recomputed every fetch (dynamic) *and* measured
  against the next projected paycheck as the default horizon (configurable via the gear).
  These are different axes, not competing options. Simplifi's "Spending Plan" then falls out
  for free as `available / days_remaining`.
- **TreeFinance / real donations: deferred to v2** — a real Stripe-to-partner payment plus a
  CO₂/trees impact model, not a virtual earmark. (Donating is a normal payment, easier than
  P2P transfers, but still its own mini-project.)
- **Out of scope (v2):** analytics UI, calendar view, multi-currency (declined),
  gamification (declined).

## Feature 1 — Recurring income → forecast (the schema fix)

### Backend

1. **Model:** add `recurrence: Mapped[Optional[str]] = mapped_column(String)` to `Income`
   (`server/src/db/models.py:118`), mirroring `Expense`.
2. **Migration:** new Alembic revision adding `income.recurrence` (nullable). Round-trip
   `upgrade`/`downgrade` on a scratch DB before applying to `budget_ai.db`.
3. **Schema:** add `recurrence: Optional[str] = Field(default=None, max_length=50)` to the
   `Income` Pydantic model (`server/src/models.py:38`, mirror `Expense` at line 34).
4. **Router:** `routers/income.py` `create_income` (and `update`) pass
   `extra_fields={"recurrence": income.recurrence}` to `TransactionService.create`
   (the create path already applies `extra_fields`).
5. **Layer A — generalize the engine** (`services/recurring_service.py`):
   - Add `project_income(user_id, start, end)` mirroring `project_expenses` (query
     `IncomeORM` where `recurrence IS NOT NULL`, tag `type: "income"`).
   - Add `project_cashflows(user_id, start, end)` → both streams merged, date-sorted, each
     tagged `type`. The pure `project_occurrences` date math is already sign-agnostic — reuse
     as-is. This is the single Layer-A read consumed by both the forecast and Safe-to-Spend.
6. **Forecast** (`services/forecast_service.py`): switch `forecast()` to `project_cashflows`;
   income days produce a **positive** `change`, expenses negative, netted per date. Add
   `total_projected_income`; `will_go_negative` / `lowest_balance` now reflect incoming pay.

### Frontend (evolve, don't add)

7. **Income entry form:** add a recurrence selector mirroring the expense form's existing one
   (same cadence list / control). The income store action sends the new field.
8. **`TimelineCard`** (`client/src/components/custom/Overview/TimelineCard.tsx`): evolve from
   "historical expenses" to a **unified cashflow chart** — keep the past-actuals area, append
   the forward projection from `GET /api/forecast/`, add a "today" reference line and an
   income-vs-expense distinction. Same card. Projected income also flows into the existing
   "Expected (recurring)" pending list in Transactions.

### Tests

- `server/tests/test_recurring.py`: new `project_income` / `project_cashflows` cases.
- `server/tests/test_forecast.py`: recurring income lifts the balance; a paycheck before a
  big bill flips `will_go_negative` from true to false.

## Feature 3 — Safe-to-Spend (evolve `SpendCard` + its gear)

### Backend (`services/spend_service.py`)

Generalize the existing `get_budget_allotment` (which already computes paycheck − fixed
costs − savings% − goal contributions) into a single source of truth:

- `safe_to_spend(user, as_of=today)` → `available`, `horizon_end`, `days_remaining`,
  `daily_plan` (= `available / days_remaining`, Simplifi's plan for free), plus a component
  **breakdown** so the UI can show *why*.
- Formula (each component config-gated):

  ```
  available = current_balance
            − upcoming_bills(to horizon, via project_cashflows)
            + projected_income(to horizon, if enabled)
            − goal_earmarks            # = Σ current Goal.progress  (earmark wiring)
            − remaining_goal_contributions
            − buffer
  ```

- **Horizon** = next projected paycheck date (from `project_income`), falling back to
  end-of-month. Dynamic: recomputed on every call; the frontend store already refetches after
  each transaction mutation.
- Surface it through the data the store **already** fetches (replace the naive
  `get_budget_allotment` feed) so `SpendCard` reads richer store fields — minimal rewiring.

### Settings

Extend per-user config: add `s2s_horizon ('paycheck'|'month'|'week')`, `s2s_include_income`,
`s2s_include_goals`, `s2s_buffer` to `User` (or a small JSON `prefs` column). Extend
`Preferences` / `PreferencesUpdate` and the `PUT /api/settings/preferences/` handler in
`routers/settings.py`, reusing the existing partial-update pattern next to `spend_warning` /
`savings_percent`.

**v3 enabler — bundle one extra nullable field here:** add `birth_year` (nullable int) to
`User` in this same settings migration. It's near-free now and unlocks v3's percentile/cohort
mechanics ("you save more than X% of people your age"), which otherwise have nothing to compare
against. See `docs/v3.md` → "v1/v2 enablers".

### Frontend (evolve the existing components)

- **`SpendCard`** (`client/src/components/custom/Overview/SpendCard.tsx`): replace the
  client-side weekly `budgetAllotment - spendOverTime` math with the server `available`. Keep
  the progress bar, warning tick, and savings note (they map onto the new breakdown). Add a
  one-line `SafeToSpend.Plan` ("$X/day for N days"). Still one card.
- **`SpendSettingsDialog`** (the gear,
  `client/src/components/custom/SpendSettingsDialog/SpendSettingsDialog.tsx`): extend into a
  **sectioned compound** dialog — *Horizon* (paycheck/month/week), *What counts* (include
  income, subtract goal earmarks, buffer), *Savings* (existing warning% + savings%). This is
  exactly the user's "small icon to change the rules behind the one number" — already present,
  just deepened.

### Tests

`server/tests/test_safe_to_spend.py`: horizon = next paycheck; component toggles change the
number; earmarks reduce it; `daily_plan = available / days_remaining`; no-paycheck fallback.

## Feature 2B — Rules engine (Layer B), surfaced contextually

A general engine on the backend, but **no standalone UI** — surfaced where money lands.

### Data model (`db/models.py` + migration)

- `Rule`: `id, user_id (FK), name, enabled (int), conditions (JSON/text), action_type
  ('notify' | 'allocate' | 'roundup'), action_params (JSON/text), **`target_kind` (str) +
  `target_id` (int)**, priority (int), created_at`.
  - ⚠️ **Generic target on purpose** (`target_kind` ∈ `{goal, …}` + `target_id`), *not* a
    hardcoded `target_goal_id`. v1 only uses `target_kind='goal'`, but this lets v3
    gamification add `target_kind='liability'` ("round-up attacks a debt boss") with **no
    migration**. See `docs/v3.md` → "v1/v2 enablers".
- `RuleExecution` (idempotency log): `id, rule_id (FK), tx_type (str), tx_id (int), fired_at,
  action_type (str), amount_cents (int), result (str)`, **unique (rule_id, tx_type, tx_id)** so
  re-imports / re-syncs never double-fire a money-moving rule. (Storing `action_type` +
  `amount_cents` + `fired_at` makes this log double as the v3 "automated-save" game-event source
  — free, no extra table.)

### Conditions (v1)

An all-of list of simple predicates over the new transaction: `category` equals/in, `amount`
>/< threshold, `title` contains, `account_id` equals. Plain serialized object — no expression
language yet.

### Actions (v1, all write `Goal.progress` / `Notification`)

- `notify` → reuse `notification_service.py` (new notification `type: "rule"`).
- `allocate` → add fixed `$X` or `pct` of the transaction amount to the target
  (`target_kind='goal'` → `Goal.progress`).
- `roundup` → round the expense up to the nearest `$1` / `$5`, add the change to the target
  (also the TreeFinance primitive, reused later). In v3 the same action with
  `target_kind='liability'` pays down a debt boss — no schema change.

### Engine (`services/rule_engine.py`)

- `RuleEngine(db).run_on_transaction(user_id, tx_type, tx_id, tx_dict)`: load enabled rules
  ordered by `priority`, evaluate conditions, check the idempotency log, execute the action,
  record a `RuleExecution`. All math in cents.
- `preview(rule, sample_txns)` — dry-run for the inline editor (no writes).

### Hook point — the single creation path

`TransactionService.create()` (`services/transaction_service.py`) already runs categorization
for expenses and applies `extra_fields`. After `self.db.flush()` (row has an id), call
`RuleEngine.run_on_transaction(...)`. Covers manual entry; the Plaid import path can call the
same engine later, protected by the same idempotency log.

### API (`routers/rules.py`, registered in `main.py`)

`GET/POST/PUT/DELETE /api/rules/` CRUD; `POST /api/rules/preview` dry-run.

### Frontend — embedded where the money lands (no new tab)

- Reusable **`RuleEditor`**: condition rows + action select + amount / round-up option.
- **Goal edit dialog** (`pages/Goals/Goals.tsx`) gains an **"Auto-fund"** section using
  `RuleEditor` with `target_goal_id` pre-bound: "Round up purchases" / "Move $X when category
  = …". A small badge on the goal card (e.g. `⟳ rounds up`) signals it's automated.
- **Budget category** (optional, same `RuleEditor` with a `notify` action): "alert me if
  {category} > $X", extending the overrun-alert mental model already present on Budgets.

### Tests

`server/tests/test_rule_engine.py`: each action type; condition matching; **idempotency**
(same tx twice fires once); priority ordering; round-up math.

## Appendix — `docs/v2.md` content (written in Step 0)

> **Finance Tracker — Deferred / v2 backlog** (parked during the income-forecast + rules +
> Safe-to-Spend work):
>
> - **Analytics / query tool** (Lunch Money "slice like a database"): backend already has
>   read primitives (`read_queries.py`, MCP transaction/category tools) but **no group-by
>   aggregation endpoint and no analytics view**. v2: one aggregation endpoint (totals by
>   category × time bucket) + an analytics surface (likely evolving the Transactions page
>   filters, not a new page).
> - **Calendar view** of daily spend / cashflow — cheap once `project_cashflows` exists
>   (pivot the forecast timeline by day); reuse the shadcn `calendar` primitive already used
>   on Goals / Transactions.
> - **Real money transfers** — v1 rule actions are virtual (`Goal.progress`). v2: real
>   intra-app transfers between **manually-managed (non-Plaid)** accounts; external transfers
>   remain out (money-transmission / Plaid Transfer territory).
> - **TreeFinance / donations** — real Stripe-to-partner payment + a CO₂ / trees impact
>   model. Its own mini-project; not a virtual earmark.
> - **Rule-based auto-categorization** — generalize the keyword / merchant categorizer into
>   user-editable categorization rules sharing the rules engine + `RuleEditor`.
> - **"If I skip Starbucks" (absence triggers)** — rules that fire on an *expected-but-absent*
>   transaction; needs a scheduler inferring missing recurrences from history. Categorically
>   harder than event-present rules; research item.
> - **Multi-currency** — declined; do first-or-never (touches every amount: currency tag +
>   FX-at-time + base/display split).
> - **Gamification** — declined; if revisited, build as an event-sourced projection
>   (`state = fold(events)`) that never writes to balances.
