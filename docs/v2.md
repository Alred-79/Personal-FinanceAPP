# v2 — Deferred / backlog

> Features intentionally parked during the [v1](./v1.md) work (income forecast + rules engine +
> Safe-to-Spend). Gamification graduated into its own doc, [v3.md](./v3.md).

- **Analytics / query tool** (Lunch Money "slice like a database"): the backend already has read
  primitives (`read_queries.py`, MCP transaction/category tools) but **no group-by aggregation
  endpoint and no analytics view**. v2: one aggregation endpoint (totals by category × time
  bucket) + an analytics surface — likely evolving the Transactions page filters, not a new page.

- **Calendar view** of daily spend / cashflow — cheap once v1's `project_cashflows` exists (pivot
  the forecast timeline by day); reuse the shadcn `calendar` primitive already used on Goals /
  Transactions.

- **Real money transfers** — v1 rule actions are virtual (`Goal.progress`). v2: real intra-app
  transfers between **manually-managed (non-Plaid)** accounts; external transfers remain out
  (money-transmission / Plaid Transfer territory).

- **TreeFinance / donations** — real Stripe-to-partner payment + a CO₂ / trees impact model.
  Its own mini-project (donating is a normal payment, easier than P2P transfers); not a virtual
  earmark.

- **Rule-based auto-categorization** — generalize the keyword / merchant categorizer
  (`categorization_service.py`) into user-editable categorization rules sharing the v1 rules engine
  + `RuleEditor`.

- **"If I skip Starbucks" (absence triggers)** — rules that fire on an *expected-but-absent*
  transaction; needs a scheduler inferring missing recurrences from history. Categorically harder
  than event-present rules; research item.

- **Multi-currency** — explicitly declined. Would touch every amount (currency tag + FX-at-time +
  base/display split). Do first-or-never; not now.

- **Gamification** — promoted to its own design doc: see [v3.md](./v3.md). (Reward saving/paydown,
  never spending; build as an event-sourced projection that never writes to balances.)
